# 客戶回饋：表單結構問題

**日期**: 2025-12-31
**來源**: 客戶針對《Ragic_ERP_表單結構分析.md》的回饋
**狀態**: 待處理

## 一、客戶原始問題

> 我們現在的洗單流程跟理想的有落差，部分受到 Ragic 功能限制，所以我們現況是每日新訂單進來後先輸入 50 跟 60，再在 99 展開。
>
> 唯一事實表是 50 還是 99 要想清楚？目前 99 是根據 50 的原始資料，接者參照其他維度表的外鍵連結細項欄位後，再把所有欄位展開完整納入。
>
> 至於 60 的問題是，理想的 60 其實是從 99 中「整理出來」的表，其實嚴格意義上不是維度表，更像是某種歸納後的統整表，這裡面有一個先後出現資料表的順序問題。
>
> 我理解我們目前不要動到現有的母系統結構與流程問題，只是 60 本身自然有帶「品牌」的維度，在分析時 60 必然要根據品牌進行分類，這一點在現在的結構分析中沒有看到。

---

## 二、問題拆解

### 2.1 現況作業流程

客戶說明實際作業順序：

```
新訂單進來 → 先輸入 50(訂單) + 60(客戶) → 再於 99(訂單明細) 展開
```

這與文件中的「理想資料流」不同，是受到 Ragic 功能限制的折衷方案。

---

### 2.2 事實表定義問題

客戶在問：**真正的「事實表」是 50 還是 99？**

| 表單 | 客戶描述 | 角色 |
|------|---------|------|
| 50 訂單 | 原始資料來源 | 訂單主檔（Header） |
| 99 明細 | 根據 50 + 各維度表外鍵，展開所有欄位 | 寬表（Denormalized） |

**現況理解**：
- 50 是「訂單層級」的事實表（一筆訂單一筆記錄）
- 99 是「訂單明細層級」的事實表（一筆訂單多筆商品記錄）
- 99 包含冗餘欄位，是展開後的寬表，適合分析用途

---

### 2.3 60 客戶表的本質問題

客戶指出一個關鍵矛盾：

| 理想情況 | 實際情況 |
|---------|---------|
| 客戶表是「維度表」| 客戶資料是從訂單「整理出來」的 |
| 應該先存在，供訂單參照 | 先有訂單，才有客戶 |

**結論**：60 在邏輯上更像是「歸納統整表」而非傳統維度表，這牽涉到資料順序問題。

---

### 2.4 品牌維度缺失（核心問題）

客戶指出文件的結構分析**缺漏**：

> 「60 本身自然有帶『品牌』的維度，在分析時 60 必然要根據品牌進行分類，這一點在現在的結構分析中沒有看到」

**文件現況**（關聯矩陣）：

```
60 客戶 → 99 明細  ✓（有標示）
60 客戶 → 10 品牌  ✗（未標示）
```

**問題影響**：
- 客戶表應該有品牌維度（例如：客戶是哪個品牌引進的）
- 目前文件沒有標示 60↔10 的關聯
- 這會影響「按品牌分析客戶」的能力

### 4.2 關鍵發現

**❌ 60 客戶表確實沒有「品牌編號」欄位**

這驗證了客戶的問題：
- 60 客戶表本身不包含品牌維度

- 需透過 99 訂單明細間接推導

## 五、解決方案

### 5.1 事實表角色釐清

| 表單 | 角色 | 粒度 | 用途 |
|------|------|------|------|
| 50 訂單管理 | 訂單事實表 | 一訂單一筆 | 訂單層級分析（金額、發票） |
| 99 訂單明細 | 明細事實表 | 一訂單多筆 | 商品層級分析（SKU、品牌） |

**結論**：50 和 99 都是事實表，只是粒度不同。99 是「展開後的寬表」，包含冗餘欄位以支援多維度分析。

---

### 5.2 客戶品牌維度解決方案

由於 60 客戶表沒有品牌欄位，需透過 99 訂單明細**間接推導**：

```
客戶品牌關聯 = 60 客戶 ←[客戶編號]→ 99 明細 ←[品牌編號]→ 10 品牌
```

#### 方案 A：分析時動態計算（建議）

在 BigQuery 建立 View，動態計算客戶的品牌歸屬：

```sql
-- 客戶品牌關聯 View
CREATE OR REPLACE VIEW `erp_backup.view_customer_brand` AS
SELECT
    c.customer_code,
    c.customer_name,
    d.brand_code,
    COUNT(*) as order_count,
    SUM(d.amount) as total_amount
FROM `erp_backup.sheet_60_customer` c
JOIN `erp_backup.sheet_99_order_detail` d
    ON c.customer_code = d.customer_code
GROUP BY c.customer_code, c.customer_name, d.brand_code;
```

**優點**：
- 不修改 Ragic 母系統
- 保持資料一致性
- 可追蹤客戶跨品牌購買行為

#### 方案 B：計算「主要品牌」標籤

若需要為每位客戶指定單一品牌歸屬：

```sql
-- 客戶主要品牌（購買次數最多）
CREATE OR REPLACE VIEW `erp_backup.view_customer_primary_brand` AS
WITH ranked AS (
    SELECT
        customer_code,
        brand_code,
        COUNT(*) as purchase_count,
        ROW_NUMBER() OVER (PARTITION BY customer_code ORDER BY COUNT(*) DESC) as rn
    FROM `erp_backup.sheet_99_order_detail`
    GROUP BY customer_code, brand_code
)
SELECT customer_code, brand_code as primary_brand
FROM ranked WHERE rn = 1;
```
