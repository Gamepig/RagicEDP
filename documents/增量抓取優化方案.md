## 現況分析

### 每日增量備份場景

- **典型資料量**：< 1,000 筆/表
- **典型時間**：< 2 秒/表
- **結論**：目前效能已經足夠

### 需要優化的場景

1. **超過 5,000 筆時的分頁處理**：目前是串行分頁，可優化為並行
2. **長時間未備份後的恢復性備份**：可能需要抓取數萬筆資料
3. **準確性問題**：確保增量條件正確捕捉所有修改的資料

## 優化方案

### 方案 1：並行分頁（推薦）

**適用場景**：增量資料超過 5,000 筆時

**原理**：當檢測到第一頁返回 5,000 筆（滿頁）時，並行發送後續頁面請求

```python
from concurrent.futures import ThreadPoolExecutor

def fetch_incremental_parallel(sheet_code, last_modified_time):
    # 先抓第一頁
    first_page = fetch_page(0)
    all_records = first_page

    if len(first_page) == PAGE_SIZE:
        # 需要分頁，並行抓取後續頁面
        with ThreadPoolExecutor(max_workers=4) as executor:
            futures = []
            for page in range(1, MAX_PAGES):
                offset = page * PAGE_SIZE
                futures.append(executor.submit(fetch_page, offset))

            for future in futures:
                records = future.result()
                if not records:
                    break
                all_records.extend(records)

    return all_records
```

**效果**：理論加速 2-4x（取決於頁數）

### 方案 2：增量時間戳精確化

**問題**：目前使用 `last_modified_time` 可能遺漏邊界時間的資料

**改進**：
- 儲存最後抓取的 `_dataTimestamp` 而非 `last_modified_time`
- 使用更精確的時間戳比對

```python

```

### 方案 3：智慧批次大小

**原理**：根據歷史增量資料量動態調整 `page_size`

```python
def get_optimal_page_size(sheet_code):
    # 查詢最近 7 天的平均增量
    avg_daily = get_avg_daily_increment(sheet_code)

    if avg_daily < 500:
        return 1000   # 小量資料用小批次，快速回應
    elif avg_daily < 2000:
        return 3000   # 中量資料
    else:
        return 5000   # 大量資料用大批次，減少 API 呼叫次數
```

## 準確性保證

### 現有機制

1. **時間戳過濾**：`where=last_modified_field_id,gt,{time_str}`
2. **狀態過濾**：`where=status_field_id,eq,Toggle-On`

### 潛在問題

1. **時間精度**：Ragic API 使用秒級時間戳，同一秒內的修改可能遺漏
2. **時區問題**：確保本地時間與 Ragic 伺服器時間一致

### 改進建議

1. **向前緩衝**：抓取時間往前推 1 分鐘，確保不遺漏邊界資料
2. **使用 _dataTimestamp**：這是 Ragic 內部的毫秒級時間戳

```python
# 改進後的增量時間
buffer_seconds = 60
safe_time = last_backup_time - timedelta(seconds=buffer_seconds)
```
