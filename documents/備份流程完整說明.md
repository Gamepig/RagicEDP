## 各步驟詳細說明

### Step 0: 初始化

**程式位置**: `BackupRunner.__init__()`

**作用**:
- 建立 Ragic API 連線客戶端
- 建立 BigQuery 連線客戶端
- 載入 10 個表格的配置資訊

**輸入**: 無

**輸出**: 初始化完成的備份執行器

---

### Step 1: 取得上次備份時間

**程式位置**: `BigQueryUploader.get_last_backup_time()`

**作用**:
- 查詢 `backup_status` 表
- 取得該表格上次備份時的「最後一筆資料修改時間」
- 作為本次增量抓取的起始條件

**SQL**:
```sql
SELECT last_record_time
FROM `erp_backup.backup_status`
WHERE sheet_code = @sheet_code
```

**輸入**: `sheet_code` (例如 '50')

**輸出**: `datetime` 或 `None` (首次備份)

**問題點**:
```
⚠️ 這裡記錄的是「資料的修改時間」，不是「備份執行時間」
   用途：下次抓取條件為「修改時間 > last_record_time」
```

---

### Step 2: 從 Ragic API 抓取增量資料

**程式位置**: `RagicClient.fetch_incremental()`

**作用**:
- 呼叫 Ragic API 抓取資料
- 使用兩個過濾條件

**API 呼叫**:
```
GET https://ap6.ragic.com/grefun/{path}?api&v=3
    &where={status_field_id},eq,Toggle-On      ← 只抓啟用的資料
    &where={modified_field_id},gt,{last_time}  ← 只抓修改時間大於上次的
    &limit=1000
```

**輸入**:
- `sheet_code`: 表格代碼
- `last_modified_time`: 上次備份時間 (來自 Step 1)

**輸出**: 符合條件的記錄列表

**問題點**:
```
⚠️ 問題 1: 只用「修改時間」作為條件
   - 無法區分「新建立」vs「被修改」
   - 需要在 Step 4 用 ragic_id 來區分

⚠️ 問題 2: 各表獨立抓取
   - 訂單表和訂單明細表各自用自己的修改時間
   - 無法保證關聯完整性
```

---

### Step 3: 資料過濾

**程式位置**: `DataFilter.filter_records()`

**作用**:
- 過濾掉「無分析價值」的資料
- 兩種模式:

| 模式 | 適用表格 | 規則 |
|------|---------|------|
| **嚴格模式** | 99 (訂單明細) | 1. _ragicId 為空 → 跳過<br>2. 訂單編號、商品編號 兩者都為空 → 跳過 |
| **寬鬆模式** | 其他 9 個表 | 主鍵為空 → 跳過 |

**輸入**: 原始記錄列表

**輸出**:
- 有效記錄列表
- 被過濾的記錄數

**問題點**:
```
✅ 這個步驟沒有問題
   - 只是初步過濾明顯無效的資料
   - 不影響備份邏輯
```

---

### Step 4: 上傳到 BigQuery

**程式位置**: `BigQueryUploader.upload_records()` → `_merge_records()`

**作用**:
- 將資料寫入對應的 BQ 表
- 區分「新增」和「更新」

**子步驟**:

```
Step 4.1: 查詢 BQ 現有的 ragic_id
┌─────────────────────────────────────────────────────────────┐
│ SELECT DISTINCT ragic_id FROM `erp_backup.sheet_50_order`   │
│                                                              │
│ 結果: existing_ids = {1001, 1002, 1003, ...}                │
└─────────────────────────────────────────────────────────────┘

Step 4.2: 分類每筆資料
┌─────────────────────────────────────────────────────────────┐
│ for record in records:                                       │
│     if record.ragic_id in existing_ids:                     │
│         to_update.append(record)  ← BQ 已有，需要更新        │
│     else:                                                    │
│         to_insert.append(record)  ← BQ 沒有，需要新增        │
└─────────────────────────────────────────────────────────────┘

Step 4.3: 執行寫入
┌─────────────────────────────────────────────────────────────┐
│ INSERT: 使用 streaming insert (500 筆/批)                    │
│ UPDATE: 使用 DML UPDATE (逐筆更新)                           │
└─────────────────────────────────────────────────────────────┘
```

**輸入**: 過濾後的有效記錄列表

**輸出**:
- `inserted`: 新增筆數
- `updated`: 更新筆數

**問題點**:
```
⚠️ 問題 1: 重複更新
   - 如果資料沒有實際變化，但修改時間更新了
   - 還是會執行 UPDATE（浪費資源）
   - 解決：比較 ragic_modified_timestamp

⚠️ 問題 2: Streaming Buffer 限制
   - 剛 INSERT 的資料無法立即 UPDATE
   - 目前處理：跳過，下次備份再處理
```

---

### Step 5: 更新備份狀態

**程式位置**: `BigQueryUploader.update_backup_status()`

**作用**:
- 更新 `backup_status` 表
- 記錄本次備份的資訊

**SQL**:
```sql
UPDATE `erp_backup.backup_status`
SET
    last_backup_time = CURRENT_TIMESTAMP(),
    last_record_time = @last_record_time,  ← 本次資料中最新的修改時間
    total_records = @total_records,
    last_fetch_count = @last_fetch_count
WHERE sheet_code = @sheet_code
```

**輸入**:
- `sheet_code`: 表格代碼
- `total_records`: BQ 表的總記錄數
- `last_fetch_count`: 本次抓取筆數
- `last_record_time`: 本次資料中最新的修改時間

**問題點**:
```
🔴 重大問題: 時間窗口漏洞

目前邏輯:
  last_record_time = 本次抓取資料中「最新的修改時間」

問題場景:
  T1: 備份開始，抓取資料
  T2: 用戶修改記錄 X (修改時間 = T2)
  T3: 備份完成

  本次抓取的資料中，最新修改時間是 T1 之前的某個時間點
  所以 last_record_time 被設為 T1 之前的時間

  下次備份條件: 修改時間 > last_record_time
  記錄 X 的修改時間 T2 > last_record_time ✓ 會被抓到

  → 這種情況沒問題

另一個問題場景:
  T1: 備份開始
  T2: 備份抓取到記錄 Y (修改時間 = T2)
  T3: 用戶又修改記錄 Y (修改時間 = T3)
  T4: 備份完成，last_record_time = T2

  下次備份條件: 修改時間 > T2
  記錄 Y 的新修改時間 T3 > T2 ✓ 會被抓到

  → 這種情況也沒問題

實際上沒有漏洞?
讓我重新思考...

真正的問題:
  如果本次「沒有抓到任何資料」
  last_record_time 不會更新
  → 沒問題

  如果本次抓到的資料，最新修改時間是 T_max
  last_record_time = T_max

  下次條件: 修改時間 > T_max
  只要資料的修改時間比 T_max 新，就會被抓到
  → 沒問題

結論: Step 5 的邏輯是正確的，沒有時間窗口漏洞
```

---

### Step 6: 寫入備份日誌

**程式位置**: `BigQueryUploader.write_backup_log()`

**作用**:
- 記錄本次備份的詳細資訊
- 用於週報統計和問題追蹤

**寫入的欄位**:
| 欄位 | 說明 |
|------|------|
| `id` | UUID |
| `backup_date` | 備份日期 |
| `backup_time` | 備份時間 |
| `sheet_code` | 表格代碼 |
| `sheet_name` | 表格名稱 |
| `records_fetched` | 從 API 抓取筆數 |
| `records_inserted` | 新增筆數 |
| `records_updated` | 更新筆數 |
| `records_filtered` | 過濾筆數 |
| `status` | success / failed / skipped |
| `error_message` | 錯誤訊息 (如果有) |
| `duration_seconds` | 執行時間 |

---

## 關鍵資料表說明

### backup_status (備份狀態表)

**用途**: 追蹤每個表的備份狀態

| 欄位 | 說明 | 用途 |
|------|------|------|
| `sheet_code` | 表格代碼 | 識別表格 |
| `last_backup_time` | 最後備份執行時間 | 監控用 |
| `last_record_time` | 最後一筆資料的修改時間 | **增量條件基準** |
| `total_records` | 該表總資料量 | 統計用 |
| `last_fetch_count` | 上次抓取筆數 | 統計用 |

### backup_logs (備份日誌表)

**用途**: 記錄每次備份的詳細資訊

- 用於生成週報
- 用於問題追蹤
- 保留歷史記錄
