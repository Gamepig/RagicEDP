## 2. 深度問題分析

### 2.1 時間窗口問題

```
時間軸：
T0: 上次備份完成，記錄 last_backup_time = T0
T1: 本次備份開始執行
T2: 抓取資料中...
T3: 用戶修改了記錄 X（修改時間 = T3）
T4: 本次備份完成，記錄 last_backup_time = T4

問題：
- 記錄 X 的修改時間 T3 在 T1~T4 之間
- 但抓取條件是「修改時間 > T0」
- 如果 T3 發生在「已經抓完該表」之後，記錄 X 會被漏掉
- 下次備份條件是「修改時間 > T4」
- 如果 T3 < T4，記錄 X 永遠被漏掉！
```

**風險等級**：🔴 高

**解決方案**：
```
方案 A：使用安全時間窗口
- 抓取條件改為「修改時間 > (上次備份時間 - 1小時)」
- 代價：可能重複抓取一些資料

方案 B：記錄備份開始時間
- 備份開始時記錄 start_time
- 備份結束時，last_backup_time = start_time（而不是結束時間）
- 確保下次備份會覆蓋執行期間的修改
```

### 2.2 關聯完整性問題（已識別）

```
場景：
- 訂單 A 在 12/29 被修改（狀態更新）
- 訂單 A 的明細在 12/25 最後修改
- 增量條件：近 2 日

結果：
- 訂單表抓到訂單 A
- 訂單明細表抓不到訂單 A 的明細（因為明細是 4 天前的）
```

**風險等級**：🟡 中

**分析**：
對於「資料分析」用途，這不是嚴重問題：
- 全量資料（手動上傳）會有完整的關聯
- 增量資料只是追蹤「哪些資料被修改」
- 分析時應該使用全量資料做 JOIN

**建議**：
- 接受現狀，不實作關聯抓取
- 在文件中明確說明這個限制
- 週報中標註「增量資料不保證關聯完整性」

---

### 2.3 重複更新問題

```
場景：
- 記錄 X 在 12/28 被修改
- 12/29 備份：抓到記錄 X，執行 UPDATE
- 12/30 記錄 X 沒有被修改
- 但 12/30 備份執行全量模式（或時間條件設定錯誤）
- 又抓到記錄 X，又執行 UPDATE

問題：
- 相同資料被多次 UPDATE，內容完全相同
- 浪費 BigQuery 資源
- Streaming Buffer 可能阻擋更新
```

**風險等級**：🟡 中

**解決方案**：
```python
# 在更新前比較 ragic_modified_timestamp
def should_update(bq_record, ragic_record):
    bq_time = bq_record.get('ragic_modified_timestamp')
    ragic_time = ragic_record.get('_dataTimestamp')

    if bq_time is None:
        return True  # BQ 沒有記錄修改時間，需要更新

    return ragic_time > bq_time  # 只有 Ragic 更新才需要同步
```

### 2.4 資料刪除問題

```
場景：
- 記錄 X 在 Ragic 中被刪除
- 但 BigQuery 不會知道這件事
- BQ 中的記錄 X 會永遠存在

問題：
- 資料不一致
- 分析結果可能包含「已刪除」的資料
```

**風險等級**：🟡 中

**分析**：
根據 v2 規劃書，「刪除資料處理：不需要」
- Ragic 使用軟刪除（狀態欄位 = Toggle-Off）
- 增量抓取條件包含「狀態 = Toggle-On」
- 被軟刪除的資料不會被抓取
- 但 BQ 中已存在的資料不會被標記為刪除

**建議**：
- 如果需要，可以定期執行「軟刪除同步」
- 查詢 BQ 中狀態為 Toggle-On 但 Ragic 已改為 Toggle-Off 的記錄
- 更新這些記錄的狀態

### 2.5 Streaming Buffer 問題（已遇到）

```
BigQuery Streaming Buffer 限制：
- 資料寫入後，會在 Streaming Buffer 中停留約 90 分鐘
- Buffer 中的資料無法被 UPDATE 或 DELETE
- 只能等待 Buffer 自動 flush
```

**風險等級**：🟡 中（已處理）

**目前解決方案**：
```python
def _update_rows(self, rows, table_name):
    for row in rows:
        try:
            self._update_single_row(row, table_name)
        except Exception as e:
            if 'streaming buffer' in str(e).lower():
                skipped_count += 1  # 跳過，下次備份再更新
            else:
                raise
```

**問題**：
- 被跳過的記錄，下次備份可能還是在 Buffer 中
- 如果同一筆資料連續被修改多次，可能永遠追不上

### 2.6 大量資料修改問題

```
場景：
- 管理員執行批次操作，一次修改 10,000 筆訂單狀態
- 增量備份抓到 10,000 筆訂單

問題：
- API 呼叫時間大增
- BigQuery 寫入時間大增
- 可能超過 Cloud Function 執行時間限制（9 分鐘）
```

**風險等級**：🟡 中

**解決方案**：
```
1. 分批處理（目前已實作 500 筆/批）
2. 增加 Cloud Function 超時時間
3. 考慮使用 Cloud Run 替代（最長 60 分鐘）
4. 實作斷點續傳機制
```

**目前防護**：

### 2.8 部分失敗問題

```
場景：
- 備份 10 個表
- 前 5 個成功
- 第 6 個失敗（API 錯誤）
- 後 4 個未執行

問題：
- 已成功的 5 個表，last_backup_time 已更新
- 失敗的表，狀態不一致
- 下次備份可能漏掉失敗期間的資料
```

**風險等級**：🟡 中

**目前處理**：
- 每個表獨立記錄狀態
- 失敗的表會記錄錯誤，下次繼續從舊的 last_backup_time 開始

**改進建議**：
- 增加失敗重試機制
- 失敗時發送告警通知

---

### 2.9 時區問題

```
涉及的時區：
- Ragic 伺服器時區
- 用戶自訂欄位「最後修改日期」的時區
- BigQuery 時區（UTC）
- Cloud Function 執行時區
- Cloud Scheduler 時區（Asia/Taipei）
```

**風險等級**：🟡 中

**目前處理**：
- 程式中使用 `datetime.utcnow()` 統一為 UTC
- Ragic 的「最後修改日期」假設為 Asia/Taipei

**潛在問題**：
- 如果 Ragic 時區假設錯誤，增量條件會出錯
- 建議：明確記錄並驗證各系統的時區

---

### 2.10 欄位變更問題

```
場景：
- Ragic 表單新增了欄位 X
- 但 BQ schema 沒有欄位 X
- 備份程式抓到欄位 X 的值，但無處存放

或：
- Ragic 表單刪除了欄位 Y
- BQ 還有欄位 Y
- 新資料的欄位 Y 為空
```

**風險等級**：🟡 中

**目前處理**：
- 完整 JSON 資料存在 `data` 欄位
- 即使 schema 不完整，原始資料不會遺失

**建議**：
- 定期檢查 Ragic 和 BQ 的欄位對應
- 提供 schema 更新腳本

### 2.11 主鍵設計問題

```
目前設計：
- 使用 ragic_id 作為主鍵
- ragic_id 在單一表內唯一

潛在問題：
- 不同表的 ragic_id 可能重複
- 如果未來需要跨表查詢，需要用 table_name + ragic_id
```

**風險等級**：🟢 低

**目前狀態**：各表獨立，ragic_id 在表內唯一，沒有問題

```
已發現並修復的問題：
```

**風險等級**：🟢 低（已處理主要問題）

### 2.13 併發執行問題

```
場景：
- Cloud Scheduler 觸發備份任務
- 上一次備份還沒執行完
- 兩個備份任務同時執行

問題：
- 同一筆資料可能被同時處理
- last_backup_time 更新衝突
- 資料重複或遺失
```

**風險等級**：🟡 中

**解決方案**：
```
1. Cloud Scheduler 設定不允許併發
2. 在程式中加入分散式鎖
3. 檢查上次備份是否完成再執行
```

## 4. 關於「關聯抓取」的深度分析

### 4.1 如果實作關聯抓取

```
流程：
1. 抓取訂單表增量資料（假設 100 筆訂單）
2. 取得這 100 筆訂單的訂單編號
3. 用訂單編號查詢訂單明細表（額外 API 呼叫）
4. 可能抓到 500 筆明細（每訂單平均 5 筆）

問題 A：API 呼叫爆炸
- 如果逐一查詢：100 次額外 API 呼叫
- 如果批次查詢：Ragic API 的 where 條件長度有限制

問題 B：不必要的更新
- 500 筆明細中，可能 400 筆沒有變化
- 但還是要檢查 BQ 是否存在 → 存在則 UPDATE
- 大量不必要的更新操作

問題 C：雙向關聯
- 如果明細被修改，要不要反過來抓訂單？
- 如果要，會形成循環

問題 D：資料一致性
- 抓訂單的時間點 T1
- 抓明細的時間點 T2
- 如果 T1~T2 之間明細被修改，資料不一致
```

### 4.2 不實作關聯抓取的影響

```
情境：資料分析用途，全量資料手動上傳

分析流程：
1. 手動上傳全量資料（一次性，包含完整關聯）
2. 每日增量備份（追蹤變更）
3. 分析時：
   - 用全量資料做基礎 JOIN
   - 用增量資料識別「哪些訂單/明細有變化」
   - 如需要最新狀態，可以用增量資料覆蓋全量資料

結論：
- 對於資料分析用途，不需要增量資料的關聯完整性
- 全量資料提供完整關聯
- 增量資料提供「變更追蹤」
```

### 4.3 建議結論

**不實作關聯抓取**，原因：
1. 複雜度高，收益低
2. 會產生大量不必要的更新
3. 資料分析用途不需要增量關聯完整性
4. 全量資料已提供完整關聯

```python
def run_backup(self):
```

### 5.3 P1：失敗重試機制

```python
def backup_sheet(self, sheet_code, max_retries=3):
    for attempt in range(max_retries):
        try:
            result = self._do_backup(sheet_code)
            return result
        except Exception as e:
            if attempt < max_retries - 1:
                logger.warning(f"Retry {attempt + 1} for {sheet_code}")
                time.sleep(5)
            else:
                logger.error(f"Failed after {max_retries} attempts")
                raise
```
