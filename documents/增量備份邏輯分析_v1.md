## 1. 問題描述

### 1.1 發現的現象

在階段 3 測試中發現：

| 表格 | 記錄數 | 不同訂單數 |
|------|--------|-----------|
| 訂單表 (50) | 111 | 111 |
| 訂單明細 (99) | 205 | 65 |

- 訂單表有 111 筆訂單，但訂單明細只有 65 個不同訂單
- 兩表共同訂單：64 個
- 訂單表獨有：47 個（舊訂單被修改狀態）
- 訂單明細獨有：1 個（新訂單 OD_251229001，42 筆明細）

### 1.2 問題本質

**當前邏輯**：只根據「最後修改時間 > 上次備份時間」抓取資料

**問題**：
1. 無法區分「新增」vs「更新」
2. 各表增量條件獨立，無法保證關聯完整性
3. 可能抓到只是狀態變更的舊資料

## 2. 備份邏輯需求

### 2.1 資料分類

備份應該能夠區分兩類資料：

| 分類 | 定義 | BigQuery 操作 |
|------|------|--------------|
| **新增資料** | Ragic 新建立的記錄，BQ 中不存在 | INSERT |
| **更新資料** | Ragic 已存在但被修改的記錄，BQ 中已存在 | UPDATE |

### 2.2 判斷邏輯

```
對於每一筆從 Ragic 抓取的記錄：

1. 檢查 BQ 是否存在該 ragic_id

2. 如果不存在 → 新增資料 → INSERT

3. 如果存在 → 比較資料
   - 如果 Ragic 修改時間 > BQ 備份時間 → 更新資料 → UPDATE
   - 如果相同 → 跳過（無變更）
```

---

## 3. Ragic 時間欄位分析

### 3.1 可用的時間欄位

經過 API 測試，Ragic 提供以下時間相關欄位：

| 欄位 | 來源 | 說明 | 可用性 |
|------|------|------|--------|
| `_dataTimestamp` | 系統自動 | Unix 時間戳（毫秒），修改時間 | ✅ 可用 |
| `_ragicCreatedTime` | 系統自動 | 創建時間（某些版本） | ⚠️ 不一定有 |
| `_ragicModifiedTime` | 系統自動 | 修改時間（某些版本） | ⚠️ 不一定有 |
| `最後修改日期` | 用戶自訂 | 用戶自訂的修改日期欄位 | ✅ 可用 |

### 3.2 API 回傳範例

```json
{
  "_ragicId": 189488,
  "_dataTimestamp": 1767055394667,
  "_star": false,
  "最後修改日期": "2025/12/29 11:25:00"
}
```

### 3.3 時間欄位問題

1. **沒有獨立的創建時間**：Ragic API 不一定回傳 `_ragicCreatedTime`
2. **只有修改時間**：`_dataTimestamp` 和「最後修改日期」都是修改時間
3. **無法從時間判斷是否為新記錄**

## 4. 解決方案

### 方案 A：以 ragic_id 為判斷基準（推薦）

**邏輯**：
```
1. 從 Ragic 抓取增量資料（修改時間 > 上次備份時間）
2. 查詢 BQ 中現有的 ragic_id 列表
3. 對於每筆資料：
   - ragic_id 不在 BQ → 新增（INSERT）
   - ragic_id 在 BQ → 更新（UPDATE）
```

**優點**：
- 簡單可靠
- 不依賴創建時間
- 已在現有程式中實作（MERGE 策略）

**缺點**：
- 需要查詢 BQ 現有 ID（效能考量）

### 方案 B：維護本地狀態表

**邏輯**：
```
1. 維護 backup_status 表，記錄每個表的：
   - 最後備份時間
   - 已備份的 ragic_id 列表（或最大 ragic_id）

2. 抓取時：
   - ragic_id > 最大已備份 ID → 新增
   - ragic_id <= 最大已備份 ID 且修改時間 > 備份時間 → 更新
```

**優點**：
- 減少 BQ 查詢
- 可追蹤備份進度

**缺點**：
- 需要維護額外狀態
- ragic_id 不一定是連續遞增的

### 方案 C：雙時間戳比較

**邏輯**：
```
1. 在 BQ 記錄中保存 ragic 的修改時間
2. 抓取時比較：
   - BQ 中無此 ragic_id → 新增
   - BQ 中有此 ragic_id 且 Ragic 修改時間 > BQ 記錄的修改時間 → 更新
   - 時間相同 → 跳過
```

**優點**：
- 精確判斷是否有變更
- 避免重複更新

**缺點**：
- 需要在 BQ 保存額外時間戳欄位

## 5. 目前程式實作狀態

### 5.1 現有邏輯（BigQueryUploader）

```python
def _merge_records(self, rows, table_name):
    # 查詢現有的 ragic_id
    existing_ids = self._get_existing_ids(table_name)

    # 分類新增和更新
    to_insert = []
    to_update = []

    for row in rows:
        if row['ragic_id'] in existing_ids:
            to_update.append(row)
        else:
            to_insert.append(row)

    # 執行新增
    if to_insert:
        self._insert_rows(to_insert, table_name)

    # 執行更新
    if to_update:
        self._update_rows(to_update, table_name)

    return len(to_insert), len(to_update)
```

### 5.2 現有邏輯評估

| 功能 | 狀態 | 說明 |
|------|------|------|
| 區分新增/更新 | ✅ 已實作 | 用 ragic_id 判斷 |
| 報告新增數量 | ✅ 已實作 | records_inserted |
| 報告更新數量 | ✅ 已實作 | records_updated |
| 避免重複更新 | ⚠️ 部分 | 有更新就更新，未比較內容 |

## 6. 改進建議

### 6.1 短期改進（不改架構）

1. **增加時間戳比較**
   - 在 BQ 保存 `ragic_modified_timestamp`（從 `_dataTimestamp` 取得）
   - 更新前比較時間戳，相同則跳過

2. **增強日誌記錄**
   - 記錄每筆資料的操作類型（INSERT/UPDATE/SKIP）
   - 週報中區分新增和更新數量

### 6.2 長期改進（架構調整）

1. **建立完整的同步狀態追蹤**
   - 記錄每個 ragic_id 的最後備份時間
   - 支援重新同步特定記錄

2. **實作雙向同步檢查**
   - 檢測 Ragic 中刪除的記錄
   - 標記 BQ 中對應記錄為已刪除

## 7. 關於訂單與訂單明細不對應問題

### 7.1 問題分析

這不是「新增 vs 更新」的問題，而是「增量完整性」問題：

- 訂單表和訂單明細表各自獨立抓取
- 抓取條件是各表自己的「最後修改時間」
- 結果：可能抓到訂單但沒抓到對應明細，或反之

### 7.2 可能的解決方案

**方案 1：關聯抓取**
```
抓取訂單後，自動抓取對應的訂單明細
缺點：API 呼叫次數大增
```

**方案 2：放寬明細抓取條件**
```
訂單明細的增量條件改為：
- 最後修改時間 > 上次備份時間
- OR 訂單編號 IN (本次抓取的訂單編號)
缺點：需要額外 API 呼叫
```

**方案 3：接受不對應（目前狀態）**
```
- 增量備份只保證各表自己的增量完整
- 關聯完整性依賴全量資料
- 分析時用全量資料做 JOIN
```

### 7.3 建議

對於增量備份系統，建議採用**方案 3**（接受不對應）：

1. 增量備份的目的是**追蹤變更**，不是保證關聯完整性
2. 關聯完整性應該由**全量資料**來保證
3. 分析時使用**全量資料做 JOIN**，而不是只用增量資料
