## 三、資料清洗架構決策

### 3.1 清洗階段：分開各表 vs 彙集大表

| 面向 | 分開各表 | 彙集大表 |
|------|---------|---------|
| **Schema 複雜度** | ✅ 各表獨立 schema | ❌ 100+ 欄位，大量 NULL |
| **清洗規則設計** | ✅ 規則針對性強 | ❌ 需判斷 sheet_code 分流 |
| **跨表關聯檢查** | ⚠️ 需 JOIN 多表 | ✅ 單表內 self-join |
| **BQ 查詢成本** | ✅ 只掃描需要的表 | ❌ 每次掃描整表 (1GB+) |
| **Schema 變更** | ✅ 單表變更不影響其他 | ❌ 任一欄位變更影響全表 |
| **分區/叢集優化** | ✅ 各表可針對性優化 | ⚠️ 只能按 sheet_code 分區 |

**決策：清洗階段採用分開各表**

理由：
1. 欄位差異大（品牌表 20 欄位 vs 訂單明細表 100 欄位）
2. 清洗規則本質不同（格式驗證 vs 關聯檢查）
3. BQ 成本考量（避免每次掃描 1GB+）

### 3.2 分析階段：保持各表 vs 彙整寬表

> **待確認**：清洗後資料用於行銷與市場分析

| 方案 | 優點 | 缺點 | 適用場景 |
|------|------|------|---------|
| **A. 保持各表** | Schema 清晰、維護簡單 | 分析時需多次 JOIN | 技術團隊直接查詢 |
| **B. 寬表（Flat Table）** | 查詢簡單、BI 友好 | 資料冗餘、更新複雜 | 行銷/業務自助分析 |
| **C. 星狀模型** | 平衡效能與彈性 | 設計較複雜 | 專業 BI + AI 分析 |

### 3.4 自動清洗流程（重要決策）

**原則**：
1. **只清洗新資料** - 不重複處理已清洗的歷史資料
2. **清洗後寫回原表** - 原表保留清洗後的乾淨資料
3. **再彙整進大表** - 只將新清洗的資料 MERGE 進分析用寬表

```
┌─────────────────────────────────────────────────────────────┐
│                    自動清洗完整流程                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Step 1: 備份新資料                                         │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ Ragic API → 取得增量資料 → 寫入 BQ 各表（raw 狀態）   │   │
│  └──────────────────────────────────────────────────────┘   │
│                            ↓                                │
│  Step 2: 清洗新資料                                         │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 載入規則庫 → 只處理本次新增的記錄 → 標記/修正異常     │   │
│  └──────────────────────────────────────────────────────┘   │
│                            ↓                                │
│  Step 3: 寫回原表                                           │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ UPDATE 原表單 SET 清洗後欄位值 WHERE _ragicId IN (新) │   │
│  │ 或新增 _cleaned = true, _cleaned_at = TIMESTAMP      │   │
│  └──────────────────────────────────────────────────────┘   │
│                            ↓                                │
│  Step 4: 彙整進大表                                         │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ MERGE INTO fact_sales_wide                           │   │
│  │ USING (新清洗資料 JOIN 維度表)                        │   │
│  │ ON _ragicId                                          │   │
│  │ WHEN MATCHED THEN UPDATE                             │   │
│  │ WHEN NOT MATCHED THEN INSERT                         │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**清洗追蹤欄位（建議新增）**：

| 欄位 | 類型 | 說明 |
|------|------|------|
| `_cleaned` | BOOLEAN | 是否已清洗 |
| `_cleaned_at` | TIMESTAMP | 清洗時間 |
| `_anomaly_count` | INT64 | 異常數量 |
| `_anomaly_types` | STRING | 異常類型（逗號分隔）|

**效率優勢**：

| 方式 | 每日處理量 | 說明 |
|------|-----------|------|
| 全量清洗 | ~460,000 筆 | ❌ 浪費資源 |
| **增量清洗** | ~6,000 筆 | ✅ 只處理新資料 |

## 五、資料清洗方案

### 5.1 清洗策略

採用**分層治理**架構：

| 層級 | 名稱 | 目標 | 對空值處理 |
|------|------|------|-----------|
| L1 | raw_data | 忠實接收 | 允許 NULL |
| L2 | staging | 格式統一 | 錯值轉 NULL |
| L3 | dwh | 分析就緒 | COALESCE 處理 |

### 5.2 清洗規則類型

| 規則類型 | 來源 | 方法 | 範例 |
|---------|------|------|------|
| **關聯規則** | 歷史組合統計 | SQL GROUP BY | 品牌 A 可用促銷 [1,2,3] |
| **數值基線** | 數值分布統計 | IQR/Z-Score | 訂單金額 < 100,000 |
| **格式模式** | 成功樣本分析 | 正則匹配 | 電話 `^09\d{8}$` |
| **合法組合** | 歷史記錄 | 交叉表 | 通路-物流有效組合 |
| **外鍵參照** | 維度表 | 存在檢查 | 郵遞區號必須存在 |

### 5.3 規則輸出格式

```yaml
# rules/association_rules.yaml

  CYT:

    first_seen: "2023-01-15"

  GMK:

    ...

# rules/numeric_baselines.yaml

  Q1: 500
  Q3: 3500
  lower_bound: -4000
  upper_bound: 8000

數量:
  min: 1
  max: 100
  typical_range: [1, 10]
```

## 六、自主學習系統

### 6.1 概念

讓系統能在清理過程中發現「規則外」問題，並自動產生新規則。

### 6.2 規則外問題類型

| 代碼 | 類型 | 說明 | 處理方式 |
|------|------|------|---------|
| N1 | 新組合 | 品牌-促銷組合從未出現 | 記錄 + 分析 |
| N2 | 模式不匹配 | 不符合已知模式但可能合法 | 持續觀察 |
| N3 | 合理超界 | 超出 IQR 但可能是新業務 | 人工審核 |
| N4 | 新值出現 | 新品牌/通路/物流 | 加入規則 |
| N5 | 跨欄位異常 | 多欄位組合異常 | 分析模式 |
| N6 | 時序異常 | 時間邏輯不尋常 | 人工審核 |

### 6.3 審核策略

| 信心度 | 頻率 | 審核方式 |
|--------|------|---------|
| ≥ 0.9 | ≥ 50 次 | 自動通過 |
| 0.7-0.9 | 10-50 次 | 建議通過 |
| 0.5-0.7 | 3-10 次 | 人工審核 |
| < 0.5 | < 3 次 | 持續觀察 |

```python
# analysis/01_null_analysis.py
import json
import pandas as pd
from pathlib import Path

CONSOLIDATED_DIR = Path("test_workspace/consolidated")

def analyze_null_rates(table_name: str) -> dict:
    """分析單一表格的空值率"""
    file_path = CONSOLIDATED_DIR / f"{table_name}.json"
    with open(file_path, 'r') as f:
        data = json.load(f)

    df = pd.DataFrame(data)
    total = len(df)

    null_stats = {}
    for col in df.columns:
        null_count = df[col].isna().sum()
        empty_count = (df[col] == '').sum()
        missing = null_count + empty_count
        null_stats[col] = {
            'missing': missing,
            'rate': round(missing / total * 100, 2)
        }

    return null_stats
```
